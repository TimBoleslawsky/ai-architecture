# ADR-0002: ONNX + ONNX Runtime over PyTorch at serving time

- **Status:** Accepted
- **Date:** 2026-11-24

## Context

The product must serve the model in production. Serving with the training
framework (PyTorch) is common but drags a large dependency into every serving
process and risks framework/py-version churn in production.

## Decision

- Training and export: PyTorch (a **dev-only** dependency).
- Serving: the model is exported to **ONNX** (opset 18, static batch) and run
  through **ONNX Runtime** (CPU provider). The serving image never installs
  PyTorch.

## Consequences

**Positive**
- Small, fast serving footprint; fewer CVEs; simpler Docker image.
- The ONNX artifact is framework-agnostic and portable to edge/other runtimes.
- Preprocessing parity is guaranteed by the registry contract (ADR-0003).

**Negative**
- Export step adds a release step and can hit exporter quirks (e.g. opset
  conversion) — mitigated by exporting with `opset_version=18` directly.

## Alternatives considered

- **Serve with PyTorch:** simplest to set up, heaviest to operate.
- **TensorRT:** faster on NVIDIA hardware but GPU-specific and harder to run locally.
